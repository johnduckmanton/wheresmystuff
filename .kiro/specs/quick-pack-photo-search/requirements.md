# Requirements Document

## Introduction

This feature adds two complementary capabilities to the home inventory management system: (1) a continuous "Quick Pack" mode where users rapidly photograph items through a persistent live viewfinder camera, with AI identifying items and presenting quick confirmation cards before creating Thing records and assigning them to the active container, and (2) a photo-based search capability where users can present a photo of an item and find visually similar things in their inventory from both the main Things view and the packing interface. Both features build on the existing AI photo analysis service, packing infrastructure, and create-and-pack workflow.

## Glossary

- **Quick_Pack_Mode**: A streamlined packing interface mode where users continuously photograph items through a persistent live viewfinder, confirm AI-suggested details via compact confirmation cards, and pack items into the selected container
- **AI_Analysis_Service**: The backend service that processes photos using the OpenAI GPT-4 Vision API to identify items, extract text, and suggest metadata
- **Photo_Search_Service**: A backend service that accepts a query photo and finds visually similar Thing records in the user's inventory using image embeddings
- **Image_Embedding**: A numerical vector representation of a photo generated by an AI model, used for computing visual similarity between images
- **Embedding_Store**: A dedicated DynamoDB table for storing image embedding vectors associated with Thing photos, keyed by inventoryId and thingId for efficient lookups and optimized query patterns
- **Packing_Interface**: The existing frontend UI component that manages the packing workflow, including mode selection, item creation, and container assignment
- **Thing**: An inventory item that can be packed into containers
- **Container**: A storage unit (box, bin, etc.) that holds Things
- **Snap_Queue**: A client-side queue that manages the pipeline of captured photos awaiting AI analysis, user confirmation, and Thing creation during Quick Pack Mode
- **Confirmation_Card**: A compact overlay UI element displayed after AI analysis completes, showing the AI-suggested name and category with accept and edit actions, enabling rapid user confirmation before Thing creation
- **Similarity_Score**: A numerical value (0 to 1) representing how visually similar two images are, computed from the cosine similarity of their embeddings
- **Inventory_System**: The backend system that manages Things, Containers, and their relationships via DynamoDB
- **Live_Viewfinder**: A persistent camera preview that remains open and active throughout a Quick Pack session, allowing the user to snap photos without the camera closing or reopening between captures

## Requirements

### Requirement 1: Quick Pack Mode Activation

**User Story:** As a user packing items into a container, I want to enter a continuous photo-capture mode, so that I can rapidly photograph and pack items without navigating through multiple screens between each item.

#### Acceptance Criteria

1. WHEN the user is in "Create New" mode within the Packing_Interface, THE Packing_Interface SHALL display a "Quick Pack" option alongside the existing creation methods (AI Photo Upload, Barcode Scan, Manual Entry)
2. WHEN the user selects "Quick Pack", THE Packing_Interface SHALL activate Quick_Pack_Mode with the currently selected Container as the target
3. IF no Container is selected when the user activates Quick_Pack_Mode, THEN THE Packing_Interface SHALL prompt the user to select a Container before proceeding
4. WHILE Quick_Pack_Mode is active, THE Packing_Interface SHALL display the Live_Viewfinder with a persistent capture button and a running count of items captured in the current session
5. WHEN the user exits Quick_Pack_Mode, THE Packing_Interface SHALL close the Live_Viewfinder, return to the creation method selector, and preserve the selected Container

### Requirement 2: Live Viewfinder and Continuous Photo Capture

**User Story:** As a user in Quick Pack Mode, I want a live camera viewfinder that stays open continuously so I can snap photos one after another without the camera closing and reopening between shots.

#### Acceptance Criteria

1. WHEN Quick_Pack_Mode is activated, THE Packing_Interface SHALL open a Live_Viewfinder that remains continuously active until the user exits Quick_Pack_Mode
2. WHEN the user taps the capture button, THE Live_Viewfinder SHALL capture the current frame as a photo, add the photo to the Snap_Queue, and remain open and ready for the next capture without closing or reinitializing the camera
3. WHEN a photo is captured, THE Snap_Queue SHALL display a thumbnail preview in a scrollable strip overlaid on or below the Live_Viewfinder
4. WHILE photos are being processed in the Snap_Queue, THE Packing_Interface SHALL display a processing indicator on each thumbnail showing its current status (uploading, analyzing, confirming, complete, failed)
5. THE Snap_Queue SHALL process photos sequentially to avoid overwhelming the AI_Analysis_Service with concurrent requests
6. WHEN the device camera is unavailable, THE Packing_Interface SHALL allow the user to select photos from the device gallery as an alternative capture method

### Requirement 3: Quick Confirm Before Thing Creation

**User Story:** As a user in Quick Pack Mode, I want to quickly confirm AI-suggested item details before each Thing is created, so that I maintain control over what gets added to my inventory without slowing down the packing flow.

#### Acceptance Criteria

1. WHEN a photo enters the Snap_Queue processing pipeline, THE AI_Analysis_Service SHALL analyze the photo and return item identification results (name, description, category, extracted text, confidence score)
2. WHEN AI analysis completes for a photo, THE Packing_Interface SHALL display a Confirmation_Card showing the AI-suggested name and category with an "Accept" button and an "Edit" button
3. WHEN the AI analysis confidence score is at or below 0.6, THE Confirmation_Card SHALL highlight the low-confidence fields with a visual warning indicator to draw the user's attention
4. WHEN the user taps "Accept" on the Confirmation_Card, THE Inventory_System SHALL create a Thing record using the AI-suggested metadata, attach the original photo, and assign the Thing to the active Container
5. WHEN the user taps "Edit" on the Confirmation_Card, THE Packing_Interface SHALL expand the Confirmation_Card to allow inline editing of the name, category, and description before the user confirms creation
6. WHEN Thing creation and packing succeeds after confirmation, THE Packing_Interface SHALL update the thumbnail status to "complete" and display the confirmed name on the thumbnail
7. THE Confirmation_Card SHALL be displayed as a compact slide-up card or overlay on the Live_Viewfinder so the camera view remains partially visible and the user can continue packing quickly

### Requirement 4: Post-Creation Editing and Session Summary

**User Story:** As a user in Quick Pack Mode, I want to tap completed items to view or edit their details after creation, and see a session summary when I exit, so that I can make corrections at my own pace.

#### Acceptance Criteria

1. WHEN the user taps a completed thumbnail in the Quick Pack strip, THE Packing_Interface SHALL open a compact detail panel showing the Thing name, description, category, and photo
2. WHEN the user edits fields in the detail panel, THE Inventory_System SHALL update the corresponding Thing record with the corrected values
3. WHILE Quick_Pack_Mode is active, THE Packing_Interface SHALL allow the user to delete a captured item by removing the Thing from the Container and from the Inventory_System
4. THE Packing_Interface SHALL display a session summary showing total items captured, items completed, and items failed when the user exits Quick_Pack_Mode

### Requirement 5: Quick Pack Error Handling

**User Story:** As a user in Quick Pack Mode, I want failed items to be handled gracefully without stopping my packing flow, so that one error does not disrupt the entire session.

#### Acceptance Criteria

1. IF AI analysis fails for a photo in the Snap_Queue, THEN THE Packing_Interface SHALL mark the thumbnail as "failed" with a retry icon and continue processing the next photo in the queue
2. IF Thing creation or container packing fails for a confirmed photo, THEN THE Packing_Interface SHALL mark the thumbnail as "failed" and retain the photo and AI analysis results for retry
3. WHEN the user taps a failed thumbnail, THE Packing_Interface SHALL offer options to retry automatic processing, open the full Thing creation form with any available AI data pre-filled, or discard the photo
4. IF network connectivity is lost during Quick_Pack_Mode, THEN THE Snap_Queue SHALL pause processing, retain all captured photos locally, and resume processing when connectivity is restored
5. WHEN the AI_Analysis_Service is unavailable (HTTP 503), THE Snap_Queue SHALL implement exponential backoff with a maximum of 3 retry attempts per photo before marking the photo as failed

### Requirement 6: Image Embedding Generation

**User Story:** As a system operator, I want image embeddings to be generated and stored for Thing photos, so that the system can support visual similarity search.

#### Acceptance Criteria

1. WHEN a Thing is created with a photo (via any creation method), THE AI_Analysis_Service SHALL generate an image embedding vector for the primary photo
2. WHEN an image embedding is generated, THE Inventory_System SHALL store the embedding vector in the Embedding_Store keyed by inventoryId and thingId
3. WHEN a Thing's primary photo is updated or replaced, THE AI_Analysis_Service SHALL regenerate the image embedding for the new photo and update the stored vector in the Embedding_Store
4. IF embedding generation fails, THEN THE Inventory_System SHALL create the Thing record without an embedding and log the failure for later retry
5. THE AI_Analysis_Service SHALL use the OpenAI embeddings API to generate image embedding vectors, maintaining consistency with the existing AI provider

### Requirement 7: Photo-Based Search Interface

**User Story:** As a user looking for a specific item, I want to take or upload a photo and find visually similar items in my inventory from both the main Things view and the packing interface, so that I can locate items I packed months ago without remembering their exact name or description.

#### Acceptance Criteria

1. THE Packing_Interface SHALL provide a "Search by Photo" action accessible from both the main Things/inventory view search area and the packing interface
2. WHEN the user activates photo search from either access point, THE Packing_Interface SHALL provide options to capture a new photo or select an existing photo from the device gallery
3. WHEN a search photo is provided, THE Photo_Search_Service SHALL generate an embedding for the query photo and compare it against stored Thing embeddings within the user's inventory in the Embedding_Store
4. WHEN search results are available, THE Packing_Interface SHALL display matching Things ranked by Similarity_Score in descending order, showing the Thing photo, name, location, and Container assignment
5. THE Photo_Search_Service SHALL return results within 5 seconds of receiving the query photo

### Requirement 8: Photo Search Results with Side-by-Side Comparison

**User Story:** As a user viewing photo search results on a mobile device, I want to see my query photo alongside each matched Thing's photo with key details and quick actions, so that I can visually confirm the match and navigate to the item.

#### Acceptance Criteria

1. WHEN displaying search results, THE Packing_Interface SHALL show a side-by-side comparison view with the query photo displayed alongside each matched Thing's photo
2. WHEN displaying each search result, THE Packing_Interface SHALL show the Similarity_Score as a percentage, the Thing name, location, and Container assignment alongside the photo comparison
3. WHEN the user taps a search result, THE Packing_Interface SHALL provide a quick action to navigate to the Thing detail view or to the Thing's Container detail view
4. THE Photo_Search_Service SHALL return a maximum of 20 results with a Similarity_Score above 0.5
5. WHEN no results have a Similarity_Score above 0.5, THE Packing_Interface SHALL display a message indicating no matching items were found and suggest using text-based search as an alternative
6. WHEN the search query photo is of poor quality or unrecognizable, THE Photo_Search_Service SHALL return an appropriate error message indicating the photo could not be processed

### Requirement 9: Embedding Storage and Management

**User Story:** As a system operator, I want embeddings to be stored in a dedicated table and managed alongside Thing lifecycle events, so that the search index stays accurate, query patterns are efficient, and storage costs are controlled.

#### Acceptance Criteria

1. WHEN a Thing is deleted, THE Inventory_System SHALL delete the associated image embedding from the Embedding_Store
2. THE Embedding_Store SHALL be a separate DynamoDB table dedicated to embedding storage, with a composite key of inventoryId (partition key) and thingId (sort key) for efficient lookups
3. WHEN a bulk import or migration creates Things with photos, THE AI_Analysis_Service SHALL queue embedding generation for each photo to avoid exceeding API rate limits
4. THE Inventory_System SHALL provide a manual backfill trigger accessible from the application settings that allows the user to initiate embedding generation for existing Things that have photos but lack embeddings on demand
5. IF the stored embedding format changes due to a model upgrade, THEN THE Inventory_System SHALL provide a migration path to regenerate embeddings for all affected Things

### Requirement 10: Rate Limiting and Cost Management

**User Story:** As a system operator, I want AI API usage from Quick Pack Mode and photo search to be rate-limited and monitored, so that costs remain predictable and the service is not abused.

#### Acceptance Criteria

1. WHILE Quick_Pack_Mode is active, THE Snap_Queue SHALL enforce a maximum processing rate of 1 photo per 3 seconds to control AI API call frequency
2. THE AI_Analysis_Service SHALL log each API call with the operation type (analysis, embedding generation, search embedding) and associated cost metrics
3. WHEN a user exceeds 50 AI analysis requests within a 1-hour window, THE AI_Analysis_Service SHALL return a rate limit response and THE Packing_Interface SHALL display a message indicating the limit has been reached
4. THE AI_Analysis_Service SHALL track monthly embedding generation and search query counts per inventory for cost monitoring
5. WHERE the system is configured with AI_MOCK_MODE enabled, THE AI_Analysis_Service SHALL use mock responses for both photo analysis and embedding generation to support development without incurring API costs

### Requirement 11: Mobile Live Viewfinder Optimization for Quick Pack

**User Story:** As an iPhone user in Quick Pack Mode, I want the live viewfinder camera experience to be fast and responsive, so that I can photograph items as quickly as I physically pack them.

#### Acceptance Criteria

1. WHEN Quick_Pack_Mode is active on a mobile device, THE Live_Viewfinder SHALL use the rear-facing camera by default with the capture button positioned for easy one-handed thumb access
2. THE Packing_Interface SHALL optimize captured photos to a maximum dimension of 1024 pixels and JPEG quality of 80% before uploading, balancing AI analysis quality with upload speed
3. WHEN a photo is captured, THE Live_Viewfinder SHALL display a brief visual flash confirmation and play a subtle haptic feedback (where supported) without interrupting the live camera preview
4. THE Packing_Interface SHALL use the existing iOS camera utilities from iosCamera.ts for camera access and the photoQueue service for managing upload sequencing
5. WHEN the device is in low-storage conditions, THE Packing_Interface SHALL warn the user and limit the Snap_Queue to 5 unprocessed photos to prevent storage exhaustion

### Requirement 12: Photo Search Embedding Serialization

**User Story:** As a developer, I want embedding vectors to be reliably serialized and deserialized for storage in the dedicated Embedding_Store table and comparison, so that search accuracy is maintained across storage and retrieval cycles.

#### Acceptance Criteria

1. THE Embedding_Store SHALL serialize embedding vectors as JSON arrays of floating-point numbers for storage in the dedicated DynamoDB embeddings table
2. FOR ALL valid embedding vectors, serializing then deserializing an embedding SHALL produce a numerically equivalent vector (round-trip property)
3. WHEN computing Similarity_Score, THE Photo_Search_Service SHALL use cosine similarity between the query embedding and stored embeddings retrieved from the Embedding_Store
4. THE Photo_Search_Service SHALL normalize all embedding vectors to unit length before storage to ensure consistent cosine similarity computation
5. IF a stored embedding fails deserialization, THEN THE Photo_Search_Service SHALL exclude the Thing from search results and log the error for investigation
